## 1. 项目背景与业务问题

雪峰滑雪租赁成立于本世纪初，扎根于云顶滑雪度假区，提供高端滑雪板、雪靴、单板及相关装备的日租服务，同时供应护目镜、头盔、雪杖等配件。公司以优质服务著称，但运营多年来仍依赖一套多人共用的 Excel 工作簿管理客户、设备和合同，该工作簿每次仅限一人操作，随着数据与公式增多运行明显变慢。

云顶度假区管理方为提升宾客体验，计划在山的另一侧开设第二家租赁点，并邀请雪峰作为独家租赁合作伙伴，但要求在一个月内提交有说服力的扩张方案。若方案通过，雪峰将获得长期独家合约；若失败，竞争对手将获邀竞标。

**核心管理问题：**

1. 现有 Excel 系统无法支持多门店并行运营与数据共享；
2. 设备借出、归还、换货缺乏单品级别的追踪，难以核算差价与退款；
3. 设备维修依赖纸质单据，维修周转慢、可靠性差、承包商绩效难以衡量；
4. 员工跨店排班、设备所在门店的归属与调拨缺乏记录；
5. 管理者缺少基于数据的经营视图（设备利用率、营收、维修周转等），无法支撑扩张决策。

## 2. 系统目标

**第一版目标（单机教学演示）**：以 DataService + localStorage 构建一个可在课堂单机运行、完整演示核心业务流程的教学型 MVP，实现：

1. 统一管理客户、设备、合同、维修与排班（单机演示范围内）；
2. 以"单品（件）"为粒度追踪设备的借出、归还与换货，自动计算差价与退款；
3. 电子化维修单，缩短维修周转并追踪承包商历史费率与绩效；
4. 记录设备归属门店与当前所在门店，支撑跨店运营演示；
5. 提供管理驾驶舱，用数据支撑扩张与运营决策。

**目标架构（后续升级，非第一版实现）**：演进为"集中式关系型数据库（CloudBase PostgreSQL）+ 真实身份认证 + 行级权限（RLS）"支撑的多用户共享系统，迁移方案见《03-系统设计》§7。

> ⚠️ 第一版登录为**模拟登录**，权限为**UI 与业务服务层模拟**，**不构成真实安全边界**，不声称支持多人协作、远程访问或并发控制。系统界面统一显示"**教学演示环境**"标识。

## 3. 利益相关者与用户角色

| 角色 | 说明 | 账号关联 | 主要诉求 |
| --- | --- | --- | --- |
| 管理员（门店经理） | 林远山及门店负责人 | ACCOUNT.role=admin → employee | 全局数据管理、排班、看经营报表 |
| 店员（前台业务员） | 各门店轮岗员工 | ACCOUNT.role=staff → employee | 快速登记客户、开合同、借出/归还/换货、报修 |
| 承包商（外部维修） | 每周到访的维修分包商 | ACCOUNT.role=contractor → contractor | 接单、更新维修进度与工时（仅限本人承接单） |

> 演示账号（见数据设计）：`admin` / `staff` / `contractor`，全部为虚构账号；管理员、店员账号关联 `employee`，承包商账号关联 `contractor`。

## 4. 功能需求

### 4.1 登录与权限（模拟）
- FR-01 提供管理员、店员、承包商三类演示账号登录（**模拟登录**，密码仅占位校验，不构成真实认证）；登录表单仅含用户名与密码，角色由 `ACCOUNT.role` 自动获取，用户不可自行选择或修改角色；
- FR-02 不同角色仅能访问其职责范围内的页面与操作（**UI 与业务服务层模拟**）；
- FR-03 承包商登录后仅能看到并更新 `contractor_id` 与自己关联的维修单。

### 4.2 基础数据管理
- FR-04 客户管理：登记/查询客户（姓名、地址、电话、邮箱、出生年份、身高、体重、鞋码），邮箱用于识别回头客；
- FR-05 设备管理：维护租赁物品（**每件物理设备唯一库存编号**、名称、描述、类别、购入日期、购入成本、零售价、日租金、技能等级、归属门店、当前所在门店），雪杖等同类设备也**逐件/逐对建档**；
- FR-06 技能等级管理：初级 / 中级 / 高级 / 专家+ 四个等级，仅滑雪板、雪靴、雪杖、单板等类别关联等级，护目镜、头盔等配件不设等级；
- FR-07 门店管理：维护门店名称、地址、电话；
- FR-08 承包商管理：维护承包商名称、联系方式、当前小时费率，并保留历史费率；
- FR-09 员工管理：维护员工信息与备注；
- FR-10 员工排班：为特定日期、门店、员工安排工作时段（08:00–22:00），员工每天最多一个班次。

### 4.3 核心租赁流程
- FR-11 创建租赁合同：关联客户与经办员工，含合同日期、租赁时长、逐项租赁物品（**单品粒度，`quantity` 恒为 1**）与应付总额；
- FR-12 借出：记录每件物品的借出时间与借出门店；
- FR-13 换货/增减：合同有效期内增加、归还或更换物品，**换货拆为"归还旧设备 + 增加新设备"两条变更记录并共享 `change_group_id`**，在变更组层面计算差价/退款；
- FR-14 归还：记录归还时间与归还门店，更新设备当前所在门店（支持归还至非租出门店）。

### 4.4 维修流程
- FR-15 创建维修单：店员发现设备故障时创建（设备须处于"在库"状态），含申请日期与故障描述，关联设备与承包商；创建后维修单状态=待维修、设备状态=维修中，并按生效日期固化 `rate_id`；
- FR-16 维修流转：被分配的承包商先"接单/开始维修"（待维修→维修中），完成时填写维修完成日期、维修工时（15 分钟步进）与备注（维修中→已完成），系统固化 `calculated_cost` 并将设备恢复在库；状态不可跳跃、不可回退，第一版不实现取消维修单；
- FR-17 费率固化：创建维修单时按生效日期选定 `rate_id`，历史账单按当时费率核算。

### 4.5 管理分析
- FR-18 驾驶舱：展示设备利用率、本月营收、平均维修周转时长、门店库存分布等 KPI 与趋势图（由系统数据按既定口径计算生成）。

## 5. 端到端业务流程

**主流程（必演示）：** 登记客户 → 创建合同 → 借出设备 → 换货（差价）→ 归还（更新门店）→ 合同完成

**辅助流程：** 发现故障 → 创建维修单 → 承包商完成维修

```text
登记/识别客户
   └─ 选择设备并创建租赁合同（quantity=1，记录借出时间与借出门店）
         └─ 合同期间增减/更换物品（换货拆两条变更记录+分组，计算差价或退款）
               └─ 归还设备并更新当前所在门店
                     └─ 全部明细归还后合同转为"已完成"
   （并行）在库设备报修 → 创建维修单（待维修、固化费率）→ 承包商接单（维修中）→ 完成维修（已完成、成本固化）
```

## 6. 业务规则（关键约束）

| 编号 | 规则 |
| --- | --- |
| BR-01 | 客户邮箱在系统内唯一（识别回头客的首选方式），可空 |
| BR-02 | 每件租赁物品拥有物理压印的唯一库存编号（`item_code` 唯一） |
| BR-03 | 技能等级仅适用于滑雪板/雪靴/雪杖/单板类别，配件等级为空 |
| BR-04 | 每份合同仅对应单一客户、单一经办员工；员工可经办多份合同 |
| BR-05 | 单品粒度：`CONTRACT_LINE.quantity` 恒为 1，`UNIQUE(contract_id, item_id)` 防止同一合同重复加入同一物品 |
| BR-06 | 合同明细记录借出时间/借出门店、归还时间/归还门店 |
| BR-07 | 换货拆为"归还旧设备 + 增加新设备"两条变更记录，共享 `change_group_id`，一次换货在单个 DataService 业务方法中原子执行 |
| BR-08 | 换货差价 =（新设备日租金 − 旧设备日租金）× 剩余租赁天数；负数表示退款；变更当天计入新设备剩余租赁天数；差价在变更组层面汇总，避免重复计算 |
| BR-09 | 每张维修单对应一件设备、一个承包商；仅员工可创建，承包商仅可更新分配给自己的单；维修单状态按"待维修→维修中→已完成"单向流转，不可跳跃、不可回退，第一版不实现取消 |
| BR-10 | 维修单创建时按生效日期固化 `rate_id`；被维修单引用的费率记录不得修改/删除；维修成本 = repair_hours × 对应 hourly_rate |
| BR-11 | 排班起止时间限定 08:00–22:00（`start_time < end_time`），员工每天最多一个班次 |
| BR-12 | 设备区分 `home_store_id`（归属，仅永久调拨时改）与 `current_store_id`（当前所在，归还/调拨时更新） |
| BR-13 | 仅当合同所有"进行中"明细均已归还后，合同才可转为"已完成"，完成时重新计算并固化最终应收总额、写入 `completed_at`；已完成合同不可重新打开 |
| BR-14 | 借出中设备不得直接报修；须先归还并关闭对应合同明细 |
| BR-15 | 管理员/店员账号关联 `employee`，承包商账号关联 `contractor`；承包商仅能访问本人承接的维修单 |
| BR-16 | 金额字段均为非负数（退款以负数 `amount_delta` 表达），日期满足 `return_time > checkout_time`、`repair_date ≥ request_date` |
| BR-17 | 引用完整性：客户被合同引用、门店被设备/排班/合同明细引用、员工被账号/合同/排班引用、承包商被账号/费率/维修单引用后不可物理删除；费率被维修单引用后不可修改或删除；DataService 实施并返回明确失败原因 |

## 10. 驾驶舱 KPI 计算口径

1. **当前设备利用率** = 当前状态为"借出中"的有效设备数 ÷ 有效设备总数。
   - 有效设备总数不含已报废设备；维修中设备计入总数，但不计入借出数。
2. **本月营收** = 本月内完成合同（按 `completed_at` 所在月份，而非 `contract_date`）的最终应收总额之和（含换货补差、扣除退款）。
3. **平均维修周转时长** = 已完成维修单的 `repair_date − request_date`（按自然日计，含周末）。
4. **门店库存分布** = 按 `current_store_id` 与设备状态（在库/借出中/维修中/已报废）汇总数量。

## 12. 测试用例正文

**TC-01 客户管理**：新增客户（必填校验）→ 重复邮箱被拒（唯一校验）→ 分页/搜索/筛选生效。

**TC-02 设备管理**：新增设备（库存编号唯一校验）→ 配件类设技能等级被拒（BR-03）→ 归属门店/当前门店必填 → 列表按门店/等级/状态筛选。

**TC-03 门店管理**：门店增删改查 → 被设备引用的门店不可物理删除。

**TC-04 承包商管理**：新增承包商+费率 → 费率历史列表 → 被维修单引用的费率不可改/删（BR-10）。

**TC-05 员工与排班**：排班时间越界（08:00–22:00 外）被拒 → 同一员工同日两班被拒 → 跨店排班可录入。

**TC-06 合同流程**：建合同（同物品重复加入被拒）→ 借出记录时间与门店 → 换货生成两条分组记录并正确计算差价/退款 → 归还更新当前门店 → 全部归还后合同转"已完成"、写入 `completed_at` 并固化总额 → 已完成合同不可重新打开。

**TC-07 维修单**：在库设备创建维修单（状态=待维修、设备→维修中、固化 rate_id）→ 借出中设备报修被拒（BR-14）→ 承包商仅见本人承接单 → 接单（待维修→维修中）→ 完成维修（维修中→已完成，必填日期/工时/备注，成本固化，设备→在库）→ 状态不可跳跃/回退。

**TC-08 驾驶舱**：核对 KPI 数值与 §10 口径一致（利用率、本月营收、平均周转、门店分布）。

**TC-09 登录与权限**：三类账号登录（仅用户名+密码，角色自动获取）进入对应视图 → 店员访问门店/承包商/员工管理页被拦截 → 承包商仅见/仅改本人维修单。

**TC-10 引用完整性删除**：被合同引用的客户、被设备/排班/合同明细引用的门店、被账号/合同/排班引用的员工、被账号/费率/维修单引用的承包商均不可删除 → 被维修单引用的费率不可改/删 → 界面显示明确失败原因。
